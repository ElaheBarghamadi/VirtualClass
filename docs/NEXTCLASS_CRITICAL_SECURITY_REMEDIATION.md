## 1. Media: what is and is not enforced

`media_token_view` rejects a member who is currently removed or waiting, but `generate_media_token` issues a LiveKit JWT for a classroom-named room, with default TTL 360 minutes. Previously issued tokens are not invalidated. `remove_member` changes DB state and notifies; `end_session` changes session/attendance and broadcasts; neither calls LiveKit. Existing LiveKit streams, permission changes, session end, old-token reconnect or room recreation are not enforced. Removing without a ban also permits rejoining an open classroom. Session is optional and room name is classroom-scoped; inviting/rejoining does not have session-generation semantics. WebSocket closure, UI state and TTL do **not** prove disconnection.

SDK `livekit-api` exposes remove/update/delete, and its request contains `revoke_token_ts`; the actual server's version, semantics, availability and reconnect behavior have not been verified. A call alone is insufficient: no durable outbox, retry worker, control-plane failure alert, version-compatible token invalidation or race-safe session generation exists. No SDK mock or real-SFU disconnect/reconnect test was executed. We deliberately did not add a superficial call that could report false success. A future design needs DB-committed authorization revocation, durable idempotent operation and retry/alert, audited result separate from authorization, fresh session-scoped rooms/tokens, explicit rejoin policy, and adversarial tests against a compatible actual LiveKit server (including outage and recovery).

`MESH_ENABLED` controls both browser selection and WebSocket `rtc_signal` relay. Default is enabled only in DEBUG; with DEBUG=false it defaults off. `.env.example` explicitly sets `MESH_ENABLED=0`. Enabling it is an explicit trusted/test deployment opt-in; mesh peers may retain established connections and exchange signals elsewhere. Disabling it cannot disconnect already established connections; restart/terminate them operationally. When LiveKit configuration or client is absent and mesh is disabled the browser selects no media, not a silent mesh fallback. These restrictions do not fix LiveKit revocation. Unit tests cover the server relay gate, not a malicious browser or real media connection.

## 2. Dependencies

On Python 3.11, the `requirements-test-lock.txt` snapshot changed Django 5.0.14 → **5.2.17** (5.2 LTS), DRF 3.17.2 → **3.18.2**, Pillow 12.3.0 → **13.0.0**. The selected versions match the highest fixes reported for those packages in the baseline scan. `requirements.txt` now sets minimums and bounded major/minor ranges consistent with these choices. Django 5.2 supports the test interpreter and local migrations and suite pass; that is not a compatibility proof for all deployment code/plugins or all supported platforms. The unhashed snapshot is not a production lock, and ranges permit other versions. Generate a reviewed, hashed lock for each deployment and scan the exact installed artifact graph; do not remove the scanner.

`pip-audit --disable-pip --no-deps -r requirements-test-lock.txt --format=json`: baseline 55 reports (13 Django, 3 DRF, 39 Pillow); after upgrades **0 known findings**, exit 0. The baseline includes two `PYSEC-2026-3717` entries, so 55 reports are not necessarily 55 unique vulnerabilities. Advisory feed and runtime environment can change. The audit covers only pinned packages in this snapshot, not OS packages, omitted dependencies, production installations, all artifact variants or unknown vulnerabilities. `pip check` found no dependency conflicts, not proof of security.

## 3. Legacy private files: operator runbook

The storage migrations change model storage only. This command does not run automatically and it **does not modify database references or delete original files**. It inventories the current DB references for `SharedFile.file`, `SharedFile.pdf_version` and `Submission.file`; it does not find unreferenced/orphaned objects, external/object storage, historical DB backups or CDN copies. Both roots must be disjoint local filesystems and names must be under `classrooms/`. It checks path traversal and existing symlinks, hashes source/destination with SHA-256, refuses conflicts and writes new files atomically without overwriting. A successful retry verifies existing destinations. Missing sources, conflicts and errors return nonzero; paths are not printed but model/PK/field identifiers are printed on stderr. A hard process crash may leave `.nextclass-copy-*` temporary files; inspect before cleanup, do not treat them as successfully migrated files. Filesystem races are not eliminated: run with writes paused and restrict root permissions.

1. Plan a maintenance/read-only window across every worker; take and **verify** independent DB and file backups, including public media, private media and volumes. Determine actual `MEDIA_ROOT` and `PRIVATE_MEDIA_ROOT`, their owner/permissions, mount availability, space and the correct database. Ensure service account can read the source and write private root; Nginx must not serve private root. No production operation has been run here.
2. Before traffic resumes, deny `/media/classrooms/` at every proxy, direct storage endpoint and CDN; purge/verify caches. Only logos should remain public. The Nginx example in `NEXTCLASS_SECURITY_AND_STABILIZATION.md` is illustrative, not a verified configuration.
3. With the actual environment and the same DB as production, run `python manage.py migrate_private_files` (dry run by default). Record the JSON counts and restricted stderr. Resolve every missing source, unsafe reference and conflict from backups; do not overwrite a divergent destination. Dry-run does not hash missing destinations and is not a backup.
4. Run `python manage.py migrate_private_files --apply`; repeat it until all references are `already_verified` and missing/conflicts/errors are zero. Original files remain intact. The command checks file content, not web-server policy, backup integrity, all metadata or orphans. Check disk permissions including pre-existing files/directories, and secure the audit output. Reconcile object counts with the DB and review skipped/unreferenced data separately.
5. Apply ordinary Django migrations according to the deployment plan and verify authorized download, denied/IDOR paths, logo access, and direct legacy URLs against the **real** proxy/storage/CDN, including cache invalidation. Do not restore traffic until verified. Retain public originals offline under restricted permissions and retention/backup policy; never delete them automatically. Rollback requires a coordinated restore of code, DB, mappings and files without reopening public access.

## 4. Concurrency and distributed execution

`start_session` locks a classroom row, and approve/deny lock relevant members inside transactions; these are local code observations, not PostgreSQL proof. `classrooms.tests_postgres_concurrency` exercises two simultaneous starts using distinct connections and checks one LIVE session, but it was skipped here: no PostgreSQL server/driver service was configured. This single test does not cover approve/deny races, rollback, process crashes, multiple workers, or every path creating sessions. Broadcasts in several operations still happen **inside** transactions: clients can see uncommitted state or a rolled-back event. In-memory Channels and cache are process-local when Redis is not configured; do not deploy them as a coordinated multi-worker control plane. Validate PostgreSQL locking/isolation, Redis failure/recovery, delivery ordering and transactional outbox/on-commit semantics in an isolated real deployment. An unsupported nonempty `DATABASE_URL` now fails closed rather than silently choosing SQLite; an empty URL still intentionally selects local SQLite and is not a safe multi-worker production setting.
